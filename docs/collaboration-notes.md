# このプロジェクトでの協働スタイル・傾向メモ

Tier表メーカーの開発を通じて観察された、指示の出し方・進め方の傾向を形式知としてまとめたものです。次回以降、同じような進め方を再現しやすくすることを目的としています。

---

## 1. 進め方の型: 「実装 → ビルド確認 → コミット → push → 確認依頼」

ほぼすべての変更で、以下のサイクルが徹底されていました。

1. コード変更
2. `npm run build` でエラーがないか確認(経験の浅いエンジニア向けに、コマンドの意味を一言添える)
3. 内容が分かるコミットメッセージでGitにコミット
4. `git push`(Vercelが自動デプロイ)
5. 「〇〇を確認してもらえますか」と、具体的にどこを見ればよいかを箇条書きで提示

→ **1回の変更ごとに必ずこのサイクルを回す**のが基本形。まとめて複数の変更を溜めてから一括で確認、というスタイルは好まれていません。

## 2. コミュニケーション手段: スクリーンショット中心

- バグ報告・デザイン修正依頼のほとんどがスクリーンショット(場合によっては「改善前/改善後」の比較画像)で行われました。
- 文章での詳細な説明は最小限で、「添付画像を参考にしてください」という指示が多い。
- → 画像から実際の見た目・状態を正確に読み取り、対応するコード箇所を特定する精度が重要。

## 3. サイズ調整は具体的な倍率で指示される

「もう少し大きく」ではなく、**「1.7倍にしてください」「2.3倍して」**のように、具体的な倍率での指示が特徴的でした。

→ 対応時は、デザインシステムの段階(Tailwindのtext-xl→text-4xlなど)の中から、指定倍率に最も近いものを選び、「◯◯倍相当としてtext-4xlを採用しました」のように換算根拠を一言添えると意図の確認がしやすい。

## 4. 一度の指示で完璧を求めず、反復修正で微調整する

- 最初の実装が意図と少しズレていても(バッジの位置、チップのデザインなど)、感情的な反応はなく「もう少し右に」「配置は添付を参考に」と簡潔に再指示される。
- 時には明確な方向転換(例: 「一覧に他人の公開Tier表が出ないようにして」→実は逆で「出るようにしたまま、非公開だけ守って」という訂正)もあったが、その際も淡々と正しい仕様を再提示するだけで、こちらの誤りを長く引きずる必要はない。

→ **完璧な一発回答より、素早く実装して確認サイクルを回す方が好まれる**。分からない詳細は「推奨案+理由」を添えて提案し、都度の指示で微調整していくスタイルが噛み合っている。

## 5. 自律的な実行を好み、逐一の承認確認は求めない

- 実装方針が決まった後は、「進めてよいですか?」と聞かずに、そのまま実装→ビルド→コミット→pushまで一気通貫で進めることが期待されている。
- 一方で、**外部サービスのアカウント作成・認証情報の入力など、Claude単独では実行できない操作**(Supabase・GitHub・Vercelでの操作)は、都度スクリーンショットを見せながら丁寧にガイドする必要がある。この時は「どこを押せばいいか」を画面の要素名で具体的に案内することが重要。

## 6. 不具合対応では「原因の説明」を欠かさない

バグ修正の際、いきなり直すのではなく「◯◯が原因でした」という一言を必ず添えてから修正する、という流れが自然に定着していました。特に以下のような、初心者には非自明な原因の説明が評価されやすい。

- Supabaseの「Automatically expose new tables」設定とGRANT文の関係
- メールリンクの事前スキャン(Outlook等)によるワンタイムコード消費
- RLSは「行の絞り込み」であり、その手前のGRANT(テーブルへのアクセス許可)とは別レイヤーであること

## 7. 開発の初心者だが、要件・設計判断は的確

- 「Web開発はほぼ初めて」と自己申告があった一方、機能要件(公開/非公開の権限設計、共同編集の範囲など)については明確な意図を持って指示されており、判断力は高い。
- 技術的な実装の詳細(dnd-kitの衝突判定、Server Actionsの仕組みなど)は都度、平易な言葉での補足説明が必要。

## 8. 常に日本語、絵文字なし、簡潔な報告を好む

- 会話はすべて日本語。技術用語も日本語で説明する。
- 冗長な前置きより、「何が変わったか」「次に何を確認すべきか」を簡潔に伝える報告スタイルが一貫して好まれている。

---

## まとめ: 次回以降も踏襲すべき型

> 小さく実装 → ビルドで検証 → コミット・push → 「ここを確認してください」と具体的に依頼 → スクリーンショットでのフィードバックを受けて微調整、を淡々と繰り返す。
> 判断に迷う細部は自分で決めて理由を添え、外部サービス操作だけは丁寧にガイドする。
